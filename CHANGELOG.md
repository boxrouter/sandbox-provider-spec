## Unreleased

- 0.5.50: adds two optional parts to SPS 1.0 itself (no `spec_version` change), claimed by gate knobs that discovery already carries, so every existing adapter is unchanged. `network.update` (`PUT /v1/sandboxes/{sandbox_id}/network`, body `{policy, allow, deny}` as in the `network_lockdown` requirement of `create`; `Provider.network_update`) replaces a running sandbox's policy; a class whose `network_lockdown` variant states `switchable: true` or `changeable: true` implements it (rule `provider-api/network-update`, section 25). Terminal reattach: `terminal.open` takes an optional caller-chosen `id` (`TerminalRequest.id`, `a-z 0-9 -`, 8 to 63 characters) that only a class claiming `terminal` with `reattach: true` accepts; such a terminal keeps running when its connection closes (`provider-api/terminal-close-ends` now speaks of a terminal opened without an `id`), `terminal.reattach` (`POST .../terminals/{id}/link`, `Provider.terminal_reattach`) returns a link to it (rule `provider-api/terminal-reattach`) and `terminal.end` (`DELETE .../terminals/{id}`, `Provider.terminal_end`) ends it (rule `provider-api/terminal-end`). The tester claims both by the knobs (`OPERATION_CLAIMS` gains `network.update`, `terminal.disconnect`, `terminal.reattach` and `terminal.end`), the 1.0 driver implements them, so `coverage.network_lockdown.switchable.true`, `coverage.network_lockdown.changeable.true` and `coverage.terminal.reattach` (and the new `coverage.terminal.end`) run on 1.0 and prove the knobs `switchable`, `changeable` and `reattach`. The OpenAPI file and its examples, the Python types, wire, `HttpProvider` and reference server, `provider-api.md` sections 16 and 25 and the implementer guide follow. The outgoing suite digest is recorded in `historical-suite-rules.json`. No declaration, vocabulary or catalog change.
- 0.5.49: the account's stored-artifacts quota gets its place in SPS 1.0 (no `spec_version` change; FA-3). The OpenAPI file (`StoredArtifacts`, the two properties), the Python types and wire codecs follow. The outgoing suite digest is recorded in `historical-suite-rules.json`. No declaration, vocabulary or catalog change.

The first public draft, format version 0.1 (`spec: sandbox-provider-spec/0.1`):

- The specification: a baseline every provider passes, 14 gates with 43 knobs, and facts
  about compute, time, place, network, hardware and environment.
- The declaration, request and run report formats, with JSON Schemas, the vocabulary as a
  catalog, and registries of region and GPU model identifiers.
- Deterministic matching rules, a reference matcher, and test vectors for independent
  implementations.
- A conformance suite of 181 tests, a runner with drivers for six providers, and the
  Docker Engine reference declaration with its run reports.
- The `sandbox-provider-spec` command: `check` validates requests, declarations and reports;
  `match` says which declarations satisfy a request and why the others do not; `run` produces
  evidence against a provider.
- Example requests for common workloads.
